# Gome Remote 단순화 재설계

상태: rev 3. 설계 결정 리뷰 2라운드 수렴(74061ee) 뒤 오너 합의. P1 통과, P2 결과로 Mac 인증을 계정 방식으로 변경(3절), 변경분 3라운드 수렴(ca473e2) 뒤 nit 반영. 등급 F.
날짜: 2026-10-05. 기준: `feat/remote-desktop` `89ab9ec`. 작업 브랜치: `redesign`.
대체 문서: `docs/ubuntu-remote-login-spec.md`, `docs/ubuntu-remote-login-plan.md`
(이 문서가 합의되면 둘은 삭제하고 git 이력으로만 남긴다).

공개 저장소이므로 이 문서에는 오너의 tailnet 로그인, 기기 이름, tailnet IP를 쓰지
않는다. 실제 값은 운영 설정과 비공개 인계 기록에만 둔다. 아래 `<owner-login>`,
"오너 Windows PC", "Mac 호스트"는 자리표시자다.

## 1. 목적과 성공 기준

오너가 말한 목적: Ubuntu 서버와 Mac을 **한 앱의 한 목록**에서 고르고, 그 앱을
**Windows와 Mac 양쪽에서** 쓴다. 오너는 Ubuntu에 이미 Windows 기본 원격
데스크톱으로 `gome` 계정에 들어가고 있다.

오너가 싫다고 한 것: 비밀번호가 너무 많음(Ubuntu 하나에 3개), 정체를 알 수 없는
전용 계정 기능, 현재 디자인(어두운 바탕+초록, 사이드바·워크스페이스·광고 문구,
설명이 많은 문구).

성공 기준(판정은 오너가 실제 기기에서 하고, 증거는 7절 형식으로 남긴다):

- S1. 앱에서 Ubuntu 타일을 누르면 바로 Ubuntu 로그인 화면(GDM)이 보이고,
  거기서 `gome` 비밀번호 하나만 넣으면 `gome`의 기존 데스크톱 세션(같은 logind 세션
  ID)에 들어간다. 앱 안에서 입력하는 비밀번호는 없다.
- S2. Mac 타일을 누르면 비밀번호 입력 없이 Mac 화면이 보이고, 잠금 해제된 Mac에서
  마우스·키보드 입력이 반영된다.
- S3. 앱이 처음 실행될 때 묻는 것은 서버 주소 하나뿐이다.
- S4. 연결을 끊었다 다시 붙어도 Ubuntu에서 열어 둔 창이 그대로다(재접속 때 GDM
  비밀번호는 다시 묻는다, 잠금 화면과 같음).
- S5. Windows 앱과 Mac 앱이 같은 화면·같은 흐름이다. 브라우저 접속도 같은 화면이다.
- S6. 목록·첫 실행·접속 중·오류 화면이 합의한 B안(6절)과 같다. 오너가 밝은/어두운
  모드 스크린샷을 보고 승인한다.

## 2. 사실 확인 (2026-10-05)

- `gome`(UID 1000, sudo 그룹, 비밀번호 없는 sudo 가능)에 GDM 원격 세션이 있다:
  `Service=gdm-password`, `Type=wayland`, `Remote=yes`, 원격 주소는 오너 Windows PC,
  시작 2026-10-01. 즉 **Windows 기본 원격 데스크톱(mstsc) → 시스템 GRD(`*:3389`) →
  GDM → `gome`** 경로는 운영에서 동작한다. **앱 경로(guacd 1.6.0/FreeRDP 2.11.7 →
  GRD → GDM)로 이 기존 세션을 넘겨받는 것은 운영에서 시험된 적이 없다.** 리허설 VM
  에서는 같은 guacd 클라이언트가 만든 세션의 재접속만 검증됐다
  (`docs/verification.md`). → 선행 시험 P1.
- 시스템 Remote Login 자격 증명은 **바꾸지 않는다**. 오너는 처음에 값을 모른다고 답했으나
  P1에서 자기 터미널(`sudo grdctl --system status --show-credentials`)로 기존 값을 확인해
  썼다(3절 결과). 이 값을 쓰는 다른 클라이언트는 오너의 Windows 원격 데스크톱이다. 에이전트는
  값을 읽거나 정하지 않는다(에이전트의 `--show-credentials` 실행 금지 유지).
- tailnet 사용자 로그인은 하나(`<owner-login>`)이고, 기기는 오너 Windows PC, macOS 2대,
  Android 폰 1대. 모두 태그 없음.
- Serve: `:8449 /` → `http://127.0.0.1:38989`(현 0.1.3 게이트웨이). `:443`에는 다른
  서비스 경로가 있으며 건드리지 않는다. Funnel 없음.
- **측정(2026-10-05, 임시 Serve 포트 → unix socket 에코 서버, 측정 뒤 제거하고 Serve
  JSON이 측정 전과 동일함을 확인)**: 일반 HTTPS 요청과 WebSocket 업그레이드 요청 모두에
  Serve가 `Tailscale-User-Login: <owner-login>`을 붙였다. 클라이언트가 위조해 보낸 같은
  헤더는 두 경우 모두 실제 로그인으로 덮어써졌다. WebSocket 에코는 양방향 동작했다.
  Origin은 그대로 전달되고, `Host`는 `localhost`, `X-Forwarded-For`는 클라이언트 tailnet
  IP였다. socket에 직접 붙은 요청에는 헤더가 없었다.
- Mac 호스트의 화면 공유 포트(5900)는 tailnet에서 응답한다. guacd VNC로 실제 Mac 화면을
  조작한 적은 없다. → 선행 시험 P2.
- 현재 비밀번호 3종: ① 게이트웨이 접속 키(`init-gateway.mjs`, 클라이언트 vault),
  ② 시스템 Remote Login 자격 증명(앱 접속 대화상자, vault), ③ GDM에서 치는 OS
  비밀번호. Mac은 VNC 비밀번호(대화상자, vault).
- 전용 계정 `gome-remote-review`(UID 1001): 예전 "앱 전용 헤드리스 데스크톱"용.
  2026-10-04 정식 로그인 방식으로 이전 완료, 비밀번호 설정됨, 실제 GDM 로그인은 오너
  미검증. 저장소의 이전·되돌리기 도구(`setup-remote-login.py` 571줄), 은퇴한
  설치기(`setup-headless.py` 219줄), legacy unit 템플릿, 테스트 466줄이 이 계정
  이전만을 위해 존재한다.

## 3. 선행 시험 (구현 착수 조건)

구현 전에 현재 0.1.3 앱과 라이브 0.1.3 게이트웨이로 오너가 직접 시험한다. 코드 변경은
없고, 게이트웨이 대상 목록에 Mac 호스트를 임시로 추가하는 것만 한다(백업 후, 재시작).

- P1. 오너가 시스템 Remote Login 값을 준비한다(실제로는 기존 값을 확인해 썼다, 결과 참고).
  Windows 0.1.3 앱에서 `ubuntu-login` 대상 → 그 값 입력 → GDM에서 `gome` 로그인. 에이전트는 전후
  `loginctl` 세션 ID·leader를 비교한다. 기대: 기존 세션(같은 ID/leader)으로 들어가고
  Windows 원격 데스크톱 쪽은 끊기며, 앱을 끊고 다시 붙어도 같은 세션이다. 오너에게
  Windows 연결이 끊긴다는 점을 미리 알렸다.
- P2. 오너가 Mac 호스트에서 VNC 비밀번호를 켠다. 0.1.3 앱에서 임시 Mac 대상 → 그 비밀번호
  → Mac 화면이 보이고 입력이 반영되는지 본다. Apple VNC 비밀번호는 8자까지만 쓰인다.

실패 시:

- P1에서 새 세션이 생기거나 로그인이 거부되면 S1/S4를 그대로 둔 채 구현하지 않는다.
  원인(FreeRDP 2.11 인계 호환 등)을 조사해 이 문서에 대안을 쓰고 다시 리뷰한다.
  D2~D7(인가·자격 증명·UI·정리)은 P1과 독립이지만, 착수는 P1 결론 뒤에 한다.
- P2가 실패하면 Mac 대상을 범위에서 빼고 원인을 보고한다. 오너 목적의 절반이므로
  오너 판단을 받는다.

결과는 이 절 아래에 날짜와 함께 기록한다.

### 결과

- 2026-10-05 P1 통과. 오너가 GNOME 설정의 "데스크톱 공유" 탭 값을 바꿨으나 시스템 Remote
  Login 값은 바뀌지 않았다(시스템 자격 증명 파일 mtime 불변). 결국 **기존 값을 그대로 썼고
  교체하지 않았다**. 오너가 자기 터미널에서 기존 값을 확인해 0.1.3 앱에 입력했다. 첫 시도
  두 번은 잘못된 값으로 NLA(NTLM MIC) 거부. 이후 앱 경로(guacd → 127.0.0.1:3389)로 GDM
  로그인했고, 시스템 GRD가 기존 세션으로 리다이렉트했다. `loginctl` 세션 ID와 leader가 시험
  전(2026-10-01부터 유지된 세션)과 같고 새 세션은 없다. 오너 확인: 열린 창 그대로, 끊고 다시
  붙어도 그대로. Windows 원격 데스크톱 연결은 넘겨졌다.
- 2026-10-05 P2 실패, 원인 확인. 0.1.3 앱은 Mac에 비밀번호만 보낸다. Mac 화면 공유는 보안
  유형으로 항상 30(Apple 원격 관리, macOS 계정 이름+비밀번호)을 맨 앞에 내놓고(VNC 비밀번호
  옵션을 켜기 전 `[30,33,36,35]`, 켠 뒤 `[30,33,36,31,32,2,35]`), guacd 1.6.0의 libvncclient는
  서버 목록에서 지원하는 첫 유형을 고른다. 같은 목록을 내놓는 루프백 가짜 RFB 서버로 guacd가
  30을 고르는 것을 측정했다(사용자 이름 유무와 무관, 30이 없으면 2를 고름). 사용자 이름 없는
  유형 30 인증은 실패하고 앱은 "연결이 끊어졌습니다"를 보인다. guacd VNC 인자에 `username`이
  있다.
- 결정(오너, 2026-10-05): Mac은 오너 본인의 macOS 로그인 계정 이름·비밀번호로 인증한다(D2).
  이 값은 그 Mac의 로그인·키체인·관리자 비밀번호이기도 하므로, 서버 장악 시 노출 범위가
  VNC 전용 비밀번호보다 크다. 오너가 이를 알고 선택했다. 오너가 켠 VNC 비밀번호 옵션은
  필요 없으므로 끄기를 권한다(약한 8자 DES 인증 경로를 닫음).
- 계정 인증으로 실제 Mac 화면이 열리는지는 0.1.3 UI가 Mac 사용자 이름 입력을 숨겨 지금 시험할
  수 없다. 새 게이트웨이 병행 후보에서 V4로 확인하며, 실패하면 Mac을 범위에서 빼고 오너
  판단을 받는다(나머지 구현은 영향 없음).

P1·P2가 남긴 상태(2026-10-05 확인):

- 오너가 바꾼 "데스크톱 공유"(사용자 수준 GRD) 값: 그 기능은 꺼져 있다(`gsettings ...rdp
  enable` = false, `grdctl status` unit inactive / RDP disabled). 수신 포트는 시스템 GRD의
  3389 하나뿐이다. 새 리스너 없음.
- 라이브 0.1.3 게이트웨이의 임시 Mac 대상: 8절 6단계에서 옛 게이트웨이와 함께 내린다. 그 전에
  필요 없으면 백업으로 되돌릴 수 있다.
- Mac의 "VNC 뷰어 암호" 옵션: 오너에게 끄기를 권했다. V4 때 상태를 확인해 기록한다.
- Mac 계정 인증의 선행 시험은 하지 않는다. 0.1.3 UI로는 사용자 이름을 보낼 수 없어 별도
  스크립트와 오너의 추가 입력이 필요하고, 실패해도 Mac만 범위에서 빠지며 나머지 구현에 영향이
  없다. 오너는 V4 실패 시 Mac 목적이 빠질 수 있음을 안다.

## 4. 결정

### D1. Ubuntu 원격 데스크톱은 `gome` 계정으로 쓴다

GDM 로그인 화면에서 `gome`으로 들어간다. 앱은 계정을 만들거나 바꾸지 않는다.
전용 계정 경로와 그 도구는 제품에서 뺀다(D7).

- `gome`은 sudo 그룹이다. 원격 데스크톱을 가진 사람은 서버 관리자 권한을 가진다.
  이는 오너가 이미 Windows 원격 데스크톱으로 쓰는 현 상태와 같다.
- 앱 접속과 Windows 기본 원격 데스크톱 접속은 같은 `gome` 세션을 놓고 경쟁하며,
  나중에 붙은 쪽이 넘겨받는다(P1에서 확인).

### D2. 기계 자격 증명은 게이트웨이가 보관하고 주입한다

시스템 Remote Login 사용자 이름/비밀번호와 Mac 로그인 계정의 사용자 이름/비밀번호(P2 결과 참고)는 게이트웨이의
자격 증명 파일(mode 600, 게이트웨이 실행 계정 `gome` 소유)에 대상 ID별로 둔다.
게이트웨이가 guacd 연결 파라미터에 넣는다. 클라이언트는 자격 증명을 보내지도,
받지도, 저장하지도 않는다. 요청에 자격 증명 필드가 있으면 400으로 거부한다.

- 근거: 게이트웨이와 guacd는 이미 원격 화면과 키 입력을 전부 복호화하는 신뢰 기계다.
  클라이언트 vault에 두더라도 매 연결마다 비밀번호가 이 서버를 지나가므로, 서버를
  장악한 공격자는 다음 연결 때 어차피 얻는다. 서버 보관이 더하는 노출은 "연결을 기다릴
  필요가 없다"는 정도다. 반면 클라이언트 보관은 기기마다 입력·저장, vault,
  Keychain/DPAPI, 서명 일관성 문제를 낳는다.
- 노출 경계(정확히): 이 서버의 `gome` 계정 전체다. `gome`의 어떤 프로세스든 자격 증명
  파일을 읽을 수 있고, 게이트웨이 socket에 직접 붙어 신원 헤더를 위조할 수 있다.
  `gome`은 비밀번호 없는 sudo가 가능하므로 사실상 서버 root와 같은 경계이며, 게이트웨이를
  다른 서비스 계정으로 돌려도 이 경계는 줄지 않는다. 따라서 별도 계정은 두지 않는다.
- 대가: 게이트웨이 인가(D3)를 통과한 기기는 Ubuntu 로그인 화면과 Mac 화면까지 비밀번호
  없이 간다. Ubuntu는 GDM 비밀번호가 여전히 막는다. **Mac은 화면 공유가 곧
  데스크톱이므로 게이트웨이 인가 = Mac 조작**이다. 오너는 "내 Tailscale 기기 전부(폰
  포함)" 범위를 선택했다(2026-10-05). 기기 분실 시 대응은 Tailscale에서 그 기기를 제거하는
  것이다.
- 보관 값의 무게: Mac 자격 증명은 오너 Mac의 로그인·키체인·관리자 비밀번호이며 서버
  파일에 평문(mode 600)으로 놓인다. 위 노출 경계(`gome` 계정 전체)에는 이 서버에서 `gome`으로
  셸과 비밀번호 없는 sudo를 가진 코딩 에이전트 세션도 포함된다. "에이전트는 값을 읽지
  않는다"는 정책이지 접근 통제가 아니다. 오너는 이를 알고 계정 인증을 선택했다(2026-10-05).
- 입력 방법: 서버에서 오너가 직접 `node scripts/set-credential.mjs <대상 ID>`를 실행하면
  에코 없이 묻고 파일에 원자적으로 쓴다(임시 파일 600 → fsync → rename). argv·환경
  변수·로그에 값이 남지 않는다. 에이전트는 이 프롬프트에 값을 넣거나 파일 내용을 출력하지
  않는다.
- 자격 증명이 없는 대상은 목록에 "설정 필요"로 보이고 접속할 수 없다.
- 대상 목록 설정 파일에는 비밀번호를 두지 않는다(편집·백업과 분리). 자격 증명 파일은
  백업하지 않는다. 잃으면 오너가 다시 입력한다.

### D3. 접속 키를 없애고 Tailscale 로그인으로 인가한다

- 게이트웨이는 TCP 포트 대신 **unix socket**(0700 디렉터리 안, 짧은 경로)으로만 듣는다.
  Serve가 이 socket을 가리킨다. 다른 OS 사용자는 Serve를 거치지 않고 게이트웨이에 닿지
  못한다. 같은 `gome` 계정 프로세스는 닿을 수 있다(D2 경계와 같음).
- `/api/*`와 `/tunnel` 업그레이드 요청은 `Tailscale-User-Login`이 설정의 `allowedLogins`
  (정확히 일치)에 있을 때만 통과한다. 헤더가 없으면(태그 기기, 직접 접근) 거부한다.
  `allowedLogins`는 **필수 설정이며 코드 기본값이 없다**. 비어 있으면 시작을 거부한다.
- Origin 검사는 유지한다: `/api/*`의 Origin은 있으면 `publicOrigin`과 같아야 하고,
  `/tunnel`은 반드시 `publicOrigin`이어야 한다(D4 이후 앱도 같은 origin). JSON
  content-type 요구도 유지한다. 이 둘이 신원 헤더 기반 인가에서 교차 사이트 요청을 막는다.
- 20초 1회용 티켓은 유지한다. 서버가 만든 연결 설정만 guacd에 가게 묶는 장치다.
- 정적 파일(UI)은 인가 없이 내려도 된다(비밀 없음). tailnet 밖에서는 Serve가 닫혀 있다.
- guacd(127.0.0.1:4822)는 지금처럼 인증 없이 루프백에 열려 있다. 로컬 프로세스가
  guacd로 대상 호스트에 붙을 수는 있지만 자격 증명은 얻지 못한다. 이 설계가 바꾸지 않는다.
- 로컬 개발: `publicOrigin`이 `http://127.0.0.1:*`일 때만 `devLogin` 설정으로 헤더를
  대신할 수 있다. 그 밖의 설정에서 `devLogin`이 있으면 시작을 거부한다.

### D4. 데스크톱 앱은 게이트웨이 화면을 띄우는 얇은 창이다

- 앱의 로컬 화면은 "서버 주소" 입력 하나뿐이다(첫 실행, 그리고 메뉴/⋯에서 변경).
  주소는 평문 설정 파일에 둔다(비밀 아님).
- 주소가 정해지면 앱 창은 `https://<게이트웨이>/`를 그대로 연다. 목록·접속·뷰어 UI는
  브라우저 접속과 **같은 코드**다.
- 앱 고유 기능(OS 메뉴바의 "원격" 메뉴, F11/전체 화면, 뷰어 상태 동기화)만 preload
  bridge로 노출한다. bridge는 창의 현재 origin이 설정된 게이트웨이 origin과 정확히 같을
  때만 동작한다. 다른 origin으로의 이동·새 창은 막는다(외부 링크는 OS 브라우저).
  `contextIsolation` on, `nodeIntegration` off, `sandbox` on.
- bridge 계약은 버전 번호를 가지며 **추가만 한다**(기존 함수의 의미를 바꾸거나 지우지
  않는다). UI는 bridge가 없거나 필요한 버전보다 낮으면 브라우저 모드(위쪽 별도 조작 줄)로
  동작한다. 앱은 서명·자동 업데이트가 없으므로, 오래된 앱도 새 UI를 쓸 수 있어야 한다.
- 제거: vault(`desktop/vault.cjs`), 토큰·자격 증명 IPC(`settings/configure/targets/
  connect/forget`), `app://` 프로토콜 UI 로딩, Linux `basic_text` 거부 로직.
- 옛 vault 파일: 새 앱은 첫 실행 때 이전 버전의 `vault.enc`(옛 토큰·자격 증명)를 지운다.
  옛 값은 새 구조에서 쓰이지 않고, 시스템 Remote Login 값은 오너가 서버에서 언제든
  확인할 수 있으며 Mac 값은 오너의 Mac 계정이므로 그 사본이 유일한 사본이 될 일이 없다.
- 근거: 현 구조는 같은 UI를 앱(`app://` + main 프로세스 HTTP 대리)과 브라우저 두 갈래로
  유지한다. 자격 증명이 클라이언트에서 사라지면 대리 계층이 필요 없다.
- 대가: 게이트웨이에 닿지 않으면 앱은 오류 화면만 보인다. 게이트웨이 없이는 어차피 아무것도
  접속할 수 없으므로 잃는 기능은 없다.

### D5. 대상 목록과 프로필

- Ubuntu 대상: 새 ID `ubuntu-server`, 이름 "Ubuntu 서버", 프로필 `gnome-remote-login`
  (127.0.0.1:3389, NLA, persistent, 기존 `ignoreCertificate` 정책 유지).
- Mac 대상: ID `mac`, Mac 호스트의 tailnet IP, 5900, VNC, 이름 "Mac"(오너 선택 2026-10-05).
- 새 게이트웨이는 새 설정 파일을 쓰며 옛 대상 ID(`ubuntu`, `ubuntu-login`)를 쓰지 않는다.
- 목록 API는 대상마다 `online`(TCP 응답)과 `ready`(자격 증명 있음)를 준다. 비밀 값은 주지
  않는다.
- Mac VNC는 16비트 색으로 연결한다(`color-depth` 16). 8비트는 macOS가 오류 515로 거부하고,
  다른 인코딩 조합은 macOS가 프레임당 약 32 MB를 보냈다(2026-10-05 측정). 그라데이션에 약한
  띠가 보일 수 있다.

## 5. 구조

```text
Windows / Mac 앱 (얇은 창)  또는 브라우저
  -> Tailscale HTTPS (Serve, Tailscale-User-Login 부여)
  -> unix socket 게이트웨이 (로그인·Origin 검사, UI 제공, 티켓 발급)
  -> 127.0.0.1:4822 guacd (읽기 전용 컨테이너, 그대로)
       -> 127.0.0.1:3389 시스템 GRD -> GDM -> gome 세션   (자격 증명 주입)
       -> Mac 호스트 tailnet IP:5900 화면 공유           (Mac 계정 이름·비밀번호 주입)
```

게이트웨이 구성 단위:

- `config.js`: 설정 검증(socket 경로, `allowedLogins`, `publicOrigin`, 대상, 자격 증명 파일
  경로). 토큰 필드가 있으면 시작 거부(옛 설정 혼용 방지).
- `credentials.js`: 자격 증명 파일 읽기·검증, 대상별 조회. 파일 권한이 600이 아니거나
  소유자가 다르면 시작 거부.
- `gateway.js`: 인가(로그인·Origin), 목록, 티켓, 정적 파일, 업그레이드.
- `tunnel.js`: guacd→클라이언트 방향 흐름 제어(backpressure). WebSocket 송신 대기량이
  상한(HIGH_WATER 1 MiB)을 넘으면 guacd 소켓 읽기를 멈추고(TCP가 guacd를 늦춘다. guacd는
  클라이언트 `sync` 응답이 늦으면 프레임을 버린다), 하한(LOW_WATER 256 KiB) 이하이거나 보낸
  프레임의 완료 콜백이 모두 끝나면 다시 읽는다. 하드 캡 HARD_CAP 32 MiB는 끝내 비우지
  않는 클라이언트나 거대한 단일 instruction에 대한 메모리 상한이며, 넘으면 닫고 내용 없는
  로그 한 줄만 남긴다. 이유: 옛 4 MiB 상한에서는 4K Mac 화면의 첫 프레임이 브라우저 소비
  속도보다 빨리 와서 터널이 약 3.5초 만에 닫혔다(2026-10-05 측정). 클라이언트→guacd 방향의
  4 MiB 상한은 그대로다.
- `scripts/set-credential.mjs`: 대화형 입력, 원자적 쓰기.

## 6. 화면 (B안, 2026-10-05 오너 선택)

시안은 저장소 밖(오너 서버의 산출물 디렉터리)에 있다.

- 밝은 미색 바탕, 기계마다 큰 타일(종류별 색 블록 + 켜짐 점 + 이름 + 상태 한 단어).
  OS 어두운 모드에서는 같은 배치의 어두운 따뜻한 톤.
- 사이드바, "워크스페이스", 광고 문구, 장식 배지 없음. 문구는 상태 한 단어 수준.
- 오른쪽 위 `⋯`: 서버 주소 바꾸기(앱), 새로고침.
- 타일을 누르면 창 전체가 원격 화면. 연결 중 스피너 + "○○에 연결하는 중".
- 앱에서는 접속 중 조작을 OS 메뉴바 "원격" 메뉴로. 브라우저는 원격 화면 위가 아닌 **위쪽
  별도 줄**에 같은 조작을 둔다(기존 방침 유지).

오류 처리:

| 상황 | 사용자에게 보이는 것 |
|---|---|
| 게이트웨이에 닿지 않음 | "서버에 연결할 수 없습니다" + 다시 시도 + 서버 주소 바꾸기 |
| 로그인 불일치/헤더 없음 (403) | "이 기기의 Tailscale 계정으로는 쓸 수 없습니다" |
| 기계 꺼짐 | 타일 흐리게 "꺼짐", 누를 수 없음 |
| 자격 증명 없음 | 타일 "설정 필요", 누를 수 없음 |
| 원격 연결 실패/끊김 | 창 가운데 "연결이 끊겼습니다 / 작업은 그대로 남아 있습니다" + 다시 연결 / 목록으로 |

내부 오류 문구와 자격 증명은 응답·로그에 넣지 않는다.

실제 서버·기기(8절 병행 후보에서, 확인 주체와 증거):

  닿는 경로가 없음. 음성 시험: `allowedLogins`를 임시로 다른 값으로 바꾸고 재시작해 실제

- V3. 오너: 끊고 다시 붙어 창 유지(S4). Windows 원격 데스크톱과 서로 넘겨받기.
- V4. 오너: Mac 타일 → Mac 화면 조작(S2).
- V5. 오너: Mac 새 앱에서 V2·V4 반복(S5). 밝은/어두운 모드 스크린샷 승인(S6).
- V6. 에이전트: 게이트웨이 재시작 후 정상 기동과 Serve 응답, 시작 거부 조건(권한·설정)이

## 8. 운영 반영과 되돌리기

새 게이트웨이를 **옛 0.1.3 게이트웨이와 나란히** 띄우고, 다 확인된 뒤 옛 것을 내린다.
같은 guacd를 함께 쓴다.

1. 새 후보 런타임을 `~/remote-candidates/<버전>`에 두고, 새 설정·빈 자격 증명 파일을
   만든다. 새 user unit(다른 이름)으로 unix socket에서 띄운다. 옛 unit·설정·:8449는
   건드리지 않는다.
2. Serve에 **새 HTTPS 포트**(예: `:8450`) 하나만 추가해 새 socket을 가리킨다. 추가 전
   Serve JSON을 백업하고, 추가 뒤 `:443`·`:8449` 경로가 그대로인지 비교한다.
3. 오너가 서버 터미널에서 `set-credential ubuntu-server`(P1에서 쓴 기존 시스템 Remote Login
   값), `set-credential mac`(오너 Mac 계정 이름·비밀번호)으로 입력한다.
4. 오너가 새 앱(Windows, Mac)을 설치하고 서버 주소로 새 포트를 넣는다. 옛 0.1.3 앱과 옛
   게이트웨이는 계속 동작한다.
5. V1~V6.
6. 통과 후: 옛 unit 중지·비활성화, Serve `:8449`만 off, 옛 설정·토큰은 비공개 백업에
   보존. 새 포트가 최종 주소가 된다(포트 번호를 8449로 되돌리지 않아 앱 주소를 다시 바꿀
   필요가 없다).

부분 실패와 되돌리기:

- 1~5 단계 중 어느 실패도 옛 경로에 영향이 없다. 새 unit 중지 + Serve 새 포트 off로 끝난다.
- 6 단계 이후 되돌리기: 보존한 옛 unit·설정으로 0.1.3 게이트웨이를 다시 켜고 Serve
